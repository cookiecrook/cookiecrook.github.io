aria-actions on ancestors

What authors expect and how it could work

w3c/aria#2883 · ARIA WG, TPAC 2026, Dublin · James Craig (@cookiecrook)

The problem

Works: on the link

<li>
  <a href="…"
    aria-actions="fave-1 del-1">ARIA</a>
  <button id="fave-1">Favorite</button>
  <button id="del-1">Delete</button>
</li>

Doesn't work: on the row

<tr aria-actions="fave-1 del-1">
  <th><a href="…">ARIA</a></th>
  <td>1.2</td> …
  <td>
    <button id="fave-1">Favorite</button>
    <button id="del-1">Delete</button>
  </td>
</tr>

Simplified from the test case.

Native example

UIKit

myView.isAccessibilityElement = true

myView.accessibilityCustomActions = [
  UIAccessibilityCustomAction(name: "Favorite",
    target: self,
    selector: #selector(favoriteItem)),
  UIAccessibilityCustomAction(name: "Delete",
    target: self,
    selector: #selector(deleteItem))
]

SwiftUI

HStack {
  // item content
}
.accessibilityElement()
.accessibilityAction(named: Text("Favorite")) {
  viewModel.favoriteItem()
}
.accessibilityAction(named: Text("Delete")) {
  viewModel.deleteItem()
}

Sources: Apple Developer Documentation · Sample code · SwiftUI accessibilityAction(named:)

On the web, aria-actions references elements, and triggering an action fires a synthesized click event on the referenced element, so pages can't easily detect assistive technology use (Design Principle 2.11). That constraint on how actions are delivered in the web shouldn't restrict authors from declaring actions on a container on behalf of its contents.

Demo: aria-actions test case

Options

  1. 1.No change in PR #1805
  2. 2.Actions either from the element, or the first ancestor with actions
  3. 3.Inherit and concatenate actions from current element and all ancestors
  4. 4.2 or 3, plus an explicit override (aria-actions="" is currently a placeholder/promise, not an override)
  5. 5.Something else?

Also considered: a redirect, e.g. aria-actionsfrom.

Discussion
